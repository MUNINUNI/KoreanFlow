# KoreanFlow 版本迭代管理规范

> 自 2026-08-18（v2.0.1）起生效。每一轮版本迭代都必须走完本规范的全部流程，缺一不可。

## 一、版本号规则（语义化版本 X.Y.Z）

| 位 | 含义 | 何时进位 |
|---|---|---|
| X 主版本 | 重大架构更新、颠覆性升级 | 如：纯前端 → 全栈（v1→v2） |
| Y 次版本 | 新增功能、模块迭代 | 如：新增复习页（v2.0→v2.1） |
| Z 修订号 | Bug 修复、细节优化、文案调整 | 如：修复录音兼容问题（v2.0.0→v2.0.1） |

## 二、每轮迭代的固定流程（5 步闭环）

```
① 完成功能开发 / 修复
        ↓
② 更新 CHANGELOG.md（复制文末模板，填写五个小节）
        ↓
③ 更新 markmap.md → 重新生成 markmap.svg
        ↓
④ 按 Conventional Commits 规范提交代码
        ↓
⑤ 推送 GitHub 远程仓库归档
```

### 第 ② 步：CHANGELOG 填写要求

- 每个版本记录五个小节：✅ 新增功能 / 🔧 功能优化 / 🐛 问题修复 / 📄 文档·思维导图更新 / 📦 仓库同步
- 条目格式：【新增】/【优化】/【修复】+ 一句话说明
- 没有内容的小节填「无」，不要删除小节

### 第 ③ 步：markmap 思维导图更新

- 思维导图**源文件是 `markmap.md`**（人用眼睛改这个）
- 改完后重新生成 `markmap.svg`（可视化成品，用 markmap 工具渲染）
- 必须更新的分支：「版本迭代」新增一行版本记录；「功能模块」勾选本次完成项；「待迭代计划」移除已完成项

### 第 ④ 步：提交信息规范（Conventional Commits）

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feat:` | 新功能 | `feat: v2.1.0 新增每日一句打卡` |
| `fix:` | 修复问题 | `fix: v2.0.2 修复录音在 Safari 无响应` |
| `docs:` | 纯文档 | `docs: 更新 CHANGELOG 与思维导图` |
| `refactor:` | 重构（不改功能） | `refactor: 抽离语料播放器组件` |
| `chore:` | 工程杂项 | `chore: 升级依赖` |

提交信息第一行带版本号，正文用列表说明改动点（参考仓库中 v2.0.0 提交）。

## 三、自动化约定（与 Kimi 的协作方式）

本项目在 Kimi 中开发。每当你对 Kimi 说「**这轮迭代完成了**」（或类似表述），Kimi 将自动执行：

1. 检查代码改动并构建验证
2. 按本规范更新 `CHANGELOG.md` 与 `markmap.md` / `markmap.svg`
3. 生成符合 Conventional Commits 的提交信息并提交
4. 推送到 GitHub 远程仓库 `MUNINUNI/KoreanFlow`
5. 用初学者能看懂的话解释本次改动与预览方法

你不需要记任何命令，只需要描述「这次做了什么」。

## 四、防坑清单

- ❌ 不要把 `.env`（数据库密码等真实密钥）提交进仓库 —— `.gitignore` 已屏蔽，不要手动强制添加
- ❌ 不要跳过 CHANGELOG 直接发版 —— 没有日志的迭代等于没有发生
- ❌ 不要改了 `markmap.md` 忘记重新生成 `markmap.svg`（反之亦然）
- ✅ 拿不准版本号进位时，对照第一节的表，或问 Kimi

## 五、CHANGELOG 迭代模板（复制使用）

```markdown
## [vX.Y.Z] - 20XX-XX-XX

### ✅ 新增功能
- 【新增】xxx

### 🔧 功能优化
- 【优化】xxx（无则填「无」）

### 🐛 问题修复
- 【修复】xxx（无则填「无」）

### 📄 文档/思维导图更新
- 更新 CHANGELOG 版本日志
- 同步更新项目 markmap 思维导图结构与内容

### 📦 仓库同步
- 本次迭代代码、文档、思维导图已全部提交推送至 GitHub 远程仓库

### 📌 待迭代计划
- xxx
```
